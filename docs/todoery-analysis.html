一句话结论 YuiTodo 现有分层架构（Riverpod + Repository + SQLite）足以承载全部目标功能，不需要推倒重来。但重复任务（Recurrence）的实现方式与 Todoery 存在本质差异，是唯一值得优先重构的底层能力——它同时影响日历、跳过、专注联动与统计准确性。

01执行摘要

Todoery 是什么

一款成熟的原生 Android 待办应用（Kotlin + Java 混合，Jetpack Compose UI，MVVM，Room + LitePal 双数据库）。它的竞争力不在"功能多"，而在于：虚拟化重复实例、分区式主页、三视图日历、多操作滑动、完整专注模式。

对 YuiTodo 的三个判断

判断结论依据
架构能否承载目标功能能Riverpod StateNotifier + Repository 已覆盖 CRUD、通知、主题、统计；新增页面与表不需要改分层
是否需要先重构建议重构一处重复任务从"每日物化"改为"虚拟实例 + 完成物化"，是日历/跳过/统计的共同底座
目标功能总工作量中—大按 5 个功能簇拆分为 4 个阶段，可增量交付

剔除项（按你的要求）

✕ 智能捕捉 Smart Capture ✕ 语音输入 / AI 语音建任务 ✕ 云存储 / Google Drive 同步 / 账号 ✕ 拍照扫描建任务 ✕ iOS / Wear OS / 多端

上述能力在 Todoery 中大量存在（尤其 PRO 付费点），但均不符合"纯本地、无联网、专注单端"的产品定位，一律不纳入。

05重复任务引擎（核心发现）

这是两家最本质的架构差异，也是 YuiTodo 现状的根因 YuiTodo 目前"每日物化一个真实任务行"；Todoery 采用"虚拟实例 + 仅完成物化"。前者会持续膨胀数据库、并产生了你之前遇到的重复任务 bug。

5.1 Todoery 的做法（反编译确认）

关键类 com.todolist.database.h（TaskDateQueryEngine）：

// database/h.java —— 按日期范围虚拟生成重复实例
TaskEntity taskEntity2 = new TaskEntity(taskEntity, false);
taskEntity2.realTaskEntity = taskEntity;   // 指回模板
taskEntity2.tempTriggerTime = j;           // 该次的触发时间
taskEntity2.setTriggerTime(j);
// 不落库，仅作为展示数据交给 UI

完成判定（database/g.java:2584）：

// 只有当"存在一条已完成、且 parentId=模板、triggerTime=该次时间"的子任务时，才算完成
if (taskEntity2.isFinish()
    && taskEntity2.getTriggerTime() == j
    && gg4.p(taskEntity2.getTaskParentId(), syncId)) {
    return Boolean.TRUE;
}

因此 Todoery 的重复模型是：

  1. 模板任务：每个重复任务只存 1 行，携带 repeatCondition。
  2. 未来/今天/过去实例：查询日期范围时实时虚拟生成（TaskDateQueryEngine），不写库。
  3. 已完成/已跳过的那一次：才物化为一行子任务（taskParentId = 模板 syncId，triggerTime = 该次时间，isFinish=true）。
  4. 跳过一次（Skip Once）：同样是"物化一条已处理子任务"，或标记排除——行为上等价于"这次已被消费"。

好处：无论重复多久，数据库只增长"实际处理过的次数"，而不是"未来所有天数"。日历跨月翻页也无需预生成。

5.2 YuiTodo 现状（源码确认）

// lib/repositories/task_repository.dart（简化）
Future<void> duplicateTaskForDate(Task original) async {
  final copy = original.copyWith(recurrenceId: original.id, ...);
  await createTask(copy);   // ← 每次都给"下一次"插入真实行
}

配合 TaskNotifier.checkAndDuplicateRecurringTasks() 在每次 loadTasks() 时扫描并补建。问题：

  • 每个到期日都新增一行，历史越久库越大；
  • 并发/重复触发易产生重复实例（你已遇到并修复过一次）；
  • 模板与实例混在同一 task 表，查询/统计需双重去重；
  • "跳过某一次"无法自然表达。

5.3 建议的 YuiTodo 目标模型

-- 模板仍为普通 task 行（保持兼容）
-- 新增：重复例外表，记录某一次被完成/跳过
CREATE TABLE task_occurrence (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id       INTEGER NOT NULL,      -- 模板任务 id
  occurrence_at INTEGER NOT NULL,      -- 该次触发的日期戳(yyyyMMdd 或 epoch)
  state         TEXT NOT NULL,         -- 'done' | 'skipped'
  completed_at  INTEGER,
  UNIQUE(task_id, occurrence_at)
);
  • 读路径：TaskDateQueryEngine 等价物——给定日期范围，从模板 + 规则算出虚拟实例，再叠加 task_occurrence 的状态。
  • 写路径：完成/跳过只写一行 occurrence，不再复制整行任务。
  • 迁移：把现有已物化的实例（recurrence_id IS NOT NULL）折叠回 occurrence，删除冗余行。
影响面：日历、首页分区、统计、通知全部受益，且是后续所有功能的地基。

06Todoery 功能全清单

6.1 首页分区（Previous / Today / Future / Completed Today）

  • 三主分区竖排，可折叠（三角图标），顺序可自定义（Settings → Task Appearance & Customize）。
  • "Previous" 聚合逾期未完成（运行态已验证：昨日 10-16 的任务显示在 "Previous (1)" 下）。
  • "Future" 聚合今天之后的任务；"Today" 为当天（含全天与定时）。
  • 底部 "Completed Today" + "Check all completed tasks" 进入完整历史。
  • 分区内任务支持长按拖拽排序（触发"切换为手动排序"提示，可勾选不再提醒）。

YuiTodo 现状：横向筛选 chip（全部/今天/明天/未来/已完成）+ 单一扁平列表，无分区、无折叠、无分区调序。

6.4 专注模式（Focus）

  • 两种计时：Timer（倒计时）/ Stopwatch（正计时）；时长范围 5 分钟 – 4 小时。
  • 可关联任务，也可"无任务专注"。
  • 支持暂停/继续、休息段（Rest）、延伸休息。
  • 记录状态：专注中 / 提前结束 / 按时完成 / 被打断；统计暂停次数、休息次数与时长。
  • 专注记录列表 + "再次专注"。

6.5 习惯（Habits）

  • 复用 TaskEntity：习惯本质是带重复规则的普通任务，集中在独立 HabitTracker 视图。
  • 指标："Total days"、连续打卡；有引导（"Start with drinking water"）。
  • 商业化：PRO 解锁无限习惯（免费受限）。

对 YuiTodo 的启示：不必新建庞大习惯系统，可复用 task + recurrence，加一个"习惯视图"即可。

09逐项可行性

9.1 重复引擎重构 前置

架构改动：新增 task_occurrence 表 + 虚拟实例查询层；迁移现有实例行。

工作量：中（2–3 天）。风险：中（数据迁移必须幂等）。

收益：根治重复 bug；日历/跳过/统计同源；为"每小时/月末/工作日"扩展留位。

9.2 首页分区 无架构改动

把现有单列表按日期分桶（逾期 / 今天 / 未来 / 今日完成），加折叠状态（存 prefs）与顺序配置。1–2 天。

9.3 日历视图 无架构改动

新增 CalendarScreen + 月历网格（自绘或 table_calendar），底部挂复用 TaskCard；读取复用虚拟实例查询。3–4 天。

依赖 9.1（虚拟查询），否则跨月翻页需物化，性能差。

9.4 滑动多操作 无架构改动

引入 flutter_slidable；新增 Skip（写 occurrence）/ Date（改期）/ Focus（跳转）动作。1–2 天。依赖 9.1 的 Skip 语义。

9.5 专注模式 +1 表

新增 focus_session 表（对应 FocusRecordEntity 字段）；FocusScreen + provider + 前后台计时（WidgetsBindingObserver 恢复）。3–4 天。

9.6 习惯追踪 复用任务

不必新建表：用 task + recurrence 建"习惯"，加 is_habit 标记或专用标签 + 习惯视图与连续打卡。若需独立统计再加 habit_log。2–3 天。

9.7 统计增强 无架构改动

加时间范围选择器（7/30/90 天）、鼓励语分级、每日完成趋势。1–2 天。

9.8 提醒增强 +列

多提醒（reminder 列表）、每任务铃声、稍后提醒。需扩展 task 表或新增 task_reminder 表。2–3 天。优先级可后置。

9.9 小组件 / 农历 / 模板 / 附件 不建议现阶段

平台原生代码量大、与"纯本地专注"定位关联弱，除非有明确需求，否则不做。

无架构改动 直接在现有分层内加 +表/列 需迁移 架构级 需先重构

12附录：建议 Schema

12.1 task_occurrence（新增）

CREATE TABLE task_occurrence (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id       INTEGER NOT NULL,       -- 模板任务
  occurrence_at INTEGER NOT NULL,       -- 该次日期戳(yyyyMMdd)
  state         TEXT NOT NULL,          -- 'done' | 'skipped'
  completed_at  INTEGER,
  UNIQUE(task_id, occurrence_at),
  FOREIGN KEY(task_id) REFERENCES task(id) ON DELETE CASCADE
);
CREATE INDEX idx_occ_task_date ON task_occurrence(task_id, occurrence_at);

12.2 focus_session（新增，Phase 2）

CREATE TABLE focus_session (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id         INTEGER,
  mode            INTEGER NOT NULL,     -- 0=TIMER 1=STOPWATCH
  status          INTEGER NOT NULL,     -- 0 focusing 1 early 2 ontime 3 interrupted
  start_time      INTEGER NOT NULL,
  end_time        INTEGER,
  target_duration INTEGER NOT NULL,     -- 秒
  actual_duration INTEGER NOT NULL,
  pause_count     INTEGER DEFAULT 0,
  rest_count      INTEGER DEFAULT 0,
  rest_duration   INTEGER DEFAULT 0,
  created_at      INTEGER NOT NULL,
  FOREIGN KEY(task_id) REFERENCES task(id) ON DELETE SET NULL
);
